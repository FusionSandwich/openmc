# Model routing and verification

User-directed working policy, updated 2026-09-25. These are assignment boundaries, not claims that any model is infallible. Preserve all existing resource, SSH, provenance and scientific gates.

## Choose the smallest suitable assignment

| Model | Assign | Do not assign without Sol review |
|---|---|---|
| GPT-6 Luna, low reasoning | One scheduled status check, specified file/hash/schema checks, mechanical edits, exact field extraction, narrow coding changes with explicit tests | Ambiguous debugging, physics interpretation, geometry qualification, normalization decisions, resource admission or production release |
| GPT-6 Sol, medium/high as needed | Orchestration, coupled implementation, diagnosing failures, experiment design, adversarial review and acceptance | Repeated healthy-job polling or mechanical work already specified for Luna |
| Astra | A concrete unresolved problem requiring deeper analysis after Sol identifies the question | Routine coordination or default review; use sparingly and state the reason |

The user's current preference is Luna for routine bounded work. Do not substitute another model silently. Reuse an appropriate existing task, avoid full-history forks and duplicate agents. Use a subagent only when a real independent task remains; delegation overhead can exceed the cost of a trivial local action.

## Every Luna assignment needs a contract

Specify: objective; exact input paths and expected identities; allowed tools/actions; files it may modify; procedure; measurable acceptance tests; output format; time/tool-call limit; and escalation conditions. Include only the relevant context. Read-only monitoring never authorizes a launch, retry, cancellation, input change, installation or scientific acceptance.

Example: Read the named checker handoff and inspect the one specified service once. Save timestamp, unit identity, observed state, exit code if available, evidence paths and observation errors. Return RUNNING, TERMINAL_CANDIDATE, FAILED or UNKNOWN. A missing service, missing file, timeout or stale receipt is UNKNOWN, not success. Then stop.

## Adversarial acceptance

A passing self-test or confident summary is insufficient. A separate Sol reviewer checks evidence and challenges the failure paths before consequential acceptance. Review only the changed logic and decisive evidence; do not duplicate the entire task.

For a checker, test or inspect handling of stale timestamps, wrong unit/run/seed, absent terminal files, nonzero exits, transport/broker errors, and a process that ended without producing valid output. For an edit, include a counterexample that would pass an incorrect implementation (wrong hash, redistributed bins, swapped units, missing values, malformed input). Preserve unknown/unsupported states rather than converting them to zero or PASS.

Review the reusable checker once against these cases. Do not pay for a fresh Sol review of every unchanged RUNNING observation. Escalate new terminal evidence, failures, contradictions and scope changes to Sol. Scientific completion and resource authorization remain Sol decisions using actual receipts.

## Scheduled monitoring

Use the existing scheduler, not sleep loops, continuous polling, or a permanently active agent. One bounded observation per scheduled wake; finish immediately when unchanged. No duplicate monitor. Notify only completion requiring validation, failure, meaningful change or user action. Stop the checker when its monitored work is finished.

Choose the interval for the specific run; never default every checker to 15 minutes. Before scheduling, record the run identity, start time, expected duration or next meaningful milestone, any known failure window, and the cost of a missed delay. Schedule the fewest observations that still catch actionable failures or completion in time. For a long healthy run, place the next check near the expected milestone or use a coarse interval; for a short test or a known early failure window, use a shorter interval only while that window matters. Back off after repeated unchanged RUNNING observations, and tighten the schedule only when new evidence changes the expected completion or risk. Record the chosen interval and why it is adequate in the handoff. Unknown duration is a reason to obtain an estimate or use a conservative coarse check, not to poll every 15 minutes.

At a scheduled wake, if that task is idle, dispatch its exact reviewed read-only check with model gpt-6-luna and low reasoning. Do not change the model of an active coupled task. If it is busy, skip the check. On terminal/failure/unknown evidence, explicitly restore gpt-6-sol before requesting diagnosis, validation or further execution. No automatic successor submissions. Active simulations continue while agents are idle.

## Compact handoff

Record current state, evidence paths/hashes, next allowed action, blockers and owner in a small durable receipt. Read this and compact task snapshots instead of replaying histories. Do not broadcast unchanged progress to other tasks. Ask another task only for a specific dependency or decision.
