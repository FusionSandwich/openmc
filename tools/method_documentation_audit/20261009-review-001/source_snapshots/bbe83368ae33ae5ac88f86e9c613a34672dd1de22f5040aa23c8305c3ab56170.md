## Why the event issue needs an assembly-level test

`CompiledFacetSurfaceSet::distance()` retains one earliest hit and ignores equal-time clean contacts. The combined-component analytic cubes therefore return component 7 or 8 depending on facet order. In native P00, `SurfaceFacetSet` erases triangles outside its XML `component_id` before creating a kernel; the 18 selectors are separate OpenMC surfaces. The priority cells use ordered Boolean regions, and `Region::distance_to_nearest_surface()` also keeps one surface token while comparing distances with `FP_PRECISION`. Therefore the combined-kernel counterexample cannot be called a native trajectory failure, but neither does the current standalone oracle prove the native layer's simultaneous or near-simultaneous crossing/owner/scoring behavior.

The derived-payload event repeat reused the retained compiled driver and exact Fraction oracle without a new build. Its exit status 1 is the expected rejection of the three unchanged analytic cube cases, not a derived-P00 hard failure. The 18-case shifts from conservative to expected unresolved show that seam repair affects numerical event classifications near selected edges/caps; they are retained in the receipt, not treated as exact equivalence. The shared compute lease was released.

The [native assembly report](P00_ASSEMBLY_REPORT_20261001.md) materially changes the gate. A direct matched-library client used 18 separate facet surfaces, actual OpenMC Region/Particle event handling and native cell-flux/surface-current scoring. In 680 query rows, baseline/current outputs, scores and exceptions agree exactly. Yet analytic touching cubes can cross correctly and then abort on the other coincident surface. With a representable `2^-48` cm positive gap, a reverse ray can retain the **farther** surface and jump from B directly to A, assigning the gap to B and current to the wrong surface. Actual HDF5 intersection-loop probes have eight first-event discrepancies and eleven continuation aborts among sixteen rays per library; exact rational certificates show strictly positive first/next contact separations. These are bounded deterministic void-model findings, not evidence that any saved production history exercised the defect. They preclude broad navigation/scoring acceptance and Step 4 performance admission until diagnosed and corrected or the supported geometric domain is explicitly restricted. A [first built-in-plane localization attempt](P00_ASSEMBLY_PLANES_PARTIAL_20261001.md) completed six touching-control rows, then stopped at a 10-second client cap. A [focused follow-up](P00_ASSEMBLY_PLANES_FOCUSED_RESULT_20261001.md) completed the current-library positive-gap control: built-in planes selected the correct B exit but assigned A as successor, skipping a real `2^-48` cm background interval. The baseline plane client timed out before rows. This localizes at least one failure to native region/particle successor handling, independent of custom facet geometry.

The [focused Pro follow-ups](https://chatgpt.com/c/6abde084-7428-83ea-b477-101034e78cb8) recommend an order-independent earliest contact group for the **independent oracle**. After the separate-surface native architecture was explained, Pro withdrew the suggestion to add a native cross-component fail-closed guard based only on the combined-kernel cube failures. The subsequent native regression did expose real shared failures. The latest Pro review separates first-contact selection, one-sided successor ownership and continuation into three independent obligations. It proposes a certified exceptional-event path at the region/particle layer: exact equal-time contacts update atomically; distinct close contacts retain their order and every positive-length interval; an unrepresentable intermediate position needs augmented state or explicit diagnostic rejection. A smaller tolerance or unconditional numerical push does not establish those obligations. Pro did not inspect or run this branch; these are repair hypotheses, not implemented fixes.

A local [source-reviewed repair design](P00_ASSEMBLY_REPAIR_DESIGN_20261001.md) converts those obligations into a staged, opt-in plan. Its first supported subset is one-level, void, axis-aligned plane navigation with exact dyadic ordering and one-sided ownership; it explicitly retains every positive interval and score. A later stage addresses separately loaded facet surfaces, true ties and the derived HDF5 intersection rays. Unsupported features must terminate diagnostically, and the existing production path remains the reference until the complete staged contract passes. The design is not an implemented fix or publication acceptance.

The [Stage 1 arithmetic checkpoint](P00_DYADIC_AXIS_CHECKPOINT_20261001.md) now implements exact binary64 coordinate differences, contact order, strict plane sides and local interval lengths. A bounded GNU14/UBSan standalone build passed directed controls and 5,520 independent Fraction differential rows; both retained libraries remained hash-identical. This is **not wired into native OpenMC navigation**: event context, complete-group successor lookup, interval scoring and lifecycle/ABI handling remain coupled work. No result in the assembly regression changed.
